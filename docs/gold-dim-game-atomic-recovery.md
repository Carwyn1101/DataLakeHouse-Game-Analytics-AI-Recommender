# Gold C03 Phase 1A: dim_game atomic recovery

[Baseline](https://github.com/Carwyn1101/DataLakeHouse-Game-Analytics-AI-Recommender/blob/6ad6002964e41ef2f4d3d0cc4e25afe44f30437f/LakeHouse_Project/scripts/silver_to_gold_etl.py#L198) computes the existing mapping and new keys, commits DELETE by AppID, then appends a lazy DataFrame. A failure between commits can make retry classify a former game as new and assign a different key. Even a successful DELETE can invalidate assumptions made by a lazy source that reads the target. The [DAG](../LakeHouse_Project/airflow/dags/silver_to_gold_etl.py) retries the task once. Bridges and all three Gold facts consume the mapping. SQL analytics and the AI index builder also read the dimension or its keys.

## Decision

Keeping split writes leaves the failure window. In-place MERGE by AppID retains all legacy duplicate rows. Matching only the highest key leaves the other rows behind. An atomic overwrite would need to replace a broader set of data and validate a different write contract.

The incremental path stages each changed or new row, with its assigned key, to private scratch Parquet. The write completes before the MERGE source is planned. Counts and MERGE read the same files. The SQL reads a direct Parquet relation and avoids the analyzed temp view failure identified in [Iceberg #7766](https://github.com/apache/iceberg/issues/7766). [Spark 3.3.2 file resolution](https://github.com/apache/spark/blob/v3.3.2/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/rules.scala#L34) and [Iceberg 1.3.1 MERGE rewriting](https://github.com/apache/iceberg/blob/apache-iceberg-1.3.1/spark/v3.3/spark-extensions/src/main/scala/org/apache/spark/sql/catalyst/analysis/RewriteMergeIntoTable.scala#L206) support the plan by source inspection.

The MERGE emits a delete action for each changed AppID and an insert action for each changed or new AppID. One delete marker matches all existing rows for that AppID. The insert marker is always unmatched and inserts the selected replacement. The highest existing key wins for a changed AppID as before. Unchanged duplicates, target-only rows, the current Silver source filter and latest-timestamp selection stay as before. Equal-timestamp input ties and null AppID behavior are outside the atomicity fix. New keys still use the target max plus row number. Schema, tracked columns, initial load, and downstream queries are unchanged.

Batch Parquet file columns are nullable in Spark. The normal initial path uses RTAS, which [passes a nullable schema to Iceberg](https://github.com/apache/spark/blob/v3.3.2/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/v2/WriteToDataSourceV2Exec.scala#L212). Confirm the native target schema, including any custom required columns, before rollout. Spark executors must be able to access the private local scratch path. Stage failure prevents MERGE, and normal and exceptional exits clean the scratch directory. Unchanged runs may stage an empty file relation but do not invoke a target write.

## Validation gates

Offline tests exercise plan calls, the exact MERGE clauses, file lifetime and scripted retry states. They do not execute Spark expressions or Iceberg commits. Merge remains **HOLD** until the following are verified on Spark 3.3.2 and Iceberg 1.3.1 in an approved disposable catalog and the Tech Lead reviews the evidence.

- [TP-19](reliability-test-plan.md): seed 101 with a lower key and 202 with a higher key. Change 101, add 303 and keep an unrelated target-only row. Include a changed duplicate AppID with distinct old keys and an unchanged duplicate. Confirm the highest legacy key remains for each changed game, changed duplicate rows are collapsed according to existing behavior, and untouched rows stay intact. Verify facts and bridges referencing surviving keys still resolve. References to lower keys already discarded by the legacy refresh policy need separate evaluation.
- [TP-25](reliability-test-plan.md): verify that staging contains the computed keys and rows before MERGE and the MERGE source plan reads scratch files. Capture snapshot IDs and full synthetic mappings. Compare an uninterrupted run with a pre-commit failure and frozen retry, plus a successful commit followed by an application-level lost acknowledgement and frozen retry. The successful change should publish one snapshot. The failed pre-commit attempt and unchanged replays should publish none. An independent reader should see either the prior mapping or the committed result.
- Verify file visibility and scratch limits for the execution topology. Enforce one writer per dimension. The atomic write does not reserve keys across concurrent max-key calculations, repair previously missing mappings, or make other Gold tables atomic.
